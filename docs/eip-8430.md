# EIP-8430: AA Transaction Type

EIP-8430, **"AA Transaction Type,"** is the sibling of [EIP-8130](/current-spec). It is a Core, Standards Track draft by Chris Hunter (@chunter-cb, Coinbase/Base), created 2026-09-23, opened as PR [#12385](https://github.com/ethereum/EIPs/pull/12385) on September 28 (the same day as PR #12386, which removed the transaction type from EIP-8130), and merged as a Draft on November 23, 2026 after 20 commits. It requires EIPs 1559, 2718, 2929, 7623, and 7702. See the [Overview](/overview) for how the two standards fit together.

::: warning Proposal status
EIP-8430 merged into `ethereum/EIPs` as a **Draft** on November 23, 2026. Draft status means the text can still change; it is not finalized. Base's [Everest upgrade](https://docs.base.org/upgrades/everest/overview) plans "Base Transactions (EIP-8430)" with no date for Sepolia or mainnet. It is not scheduled for Ethereum L1.
:::

EIP-8430 works for today's EOAs with nothing but their secp256k1 key. Its validation is fixed-cost: nodes verify one signature per role and check nonce, balance, and validity window, and never simulate wallet code. Its authenticator selector, authorization-rules hook, and reserved account-change types are the extension points EIP-8130's Keystore fills.

Spec source: [github.com/ethereum/EIPs/blob/master/EIPS/eip-8430.md](https://github.com/ethereum/EIPs/blob/master/EIPS/eip-8430.md). Discussion: [ethereum-magicians.org/t/eip-8430-aa-transaction-type-split-out-from-8130/29810](https://ethereum-magicians.org/t/eip-8430-aa-transaction-type-split-out-from-8130/29810).

## Transaction Format

```
AA_TX_TYPE || rlp([
  chain_id,
  sender,             // empty = recover from sender_auth | 20-byte address
  nonce_key,          // uint256 nonce channel
  nonce_sequence,     // uint64
  valid_after,        // uint64, seconds or milliseconds; 0 = no lower bound
  valid_before,       // uint64, seconds or milliseconds; 0 = no expiry
  max_priority_fee_per_gas,
  max_fee_per_gas,
  gas_limit,
  account_changes,    // typed entries
  calls,              // [[call, ...], ...]
  metadata,           // opaque bytes
  payer,              // empty = self-pay | 0x00 = open | 20-byte address
  sender_auth,
  payer_auth
])
call = rlp([to, value, data])
```

| Constant | Value |
|---|---|
| `AA_TX_TYPE` | `0x79` |
| `AA_PAYER_TYPE` | `0x7A`, payer signature domain only |
| `REPLAY_ID_TYPE` | `0x7901` |
| `K1_AUTHENTICATOR` | `address(1)` |
| `NONCE_MANAGER_ADDRESS` | `0x813000000000000000000000000000000000aa01` |
| `TX_CONTEXT_ADDRESS` | `0x813000000000000000000000000000000000aa02` |
| `NONCE_KEY_MAX` | `2^256 - 1` |
| `TIMESTAMP_MS_THRESHOLD` | `100_000_000_000` |
| `NONCE_FREE_EXPIRY_WINDOW` | Chain parameter (e.g. 30 seconds) |
| `REPLAY_BUFFER_CAPACITY` | Chain parameter |
| `MAX_AUTHENTICATION_GAS` | Configurable, suggested 100,000 |
| `COLD_ACCOUNT_ACCESS`, `WARM_ACCESS` | `2600`, `100` (EIP-2929), or `3000`, `100` where EIP-8038 is active |

`valid_after` and `valid_before` are read as seconds below `10^11` and as milliseconds at or above it, a rule that is a pure function of the value and therefore consensus-safe. It was introduced in EIP-8130 PR [#12204](https://github.com/ethereum/EIPs/pull/12204) before the split.

## Authentication

The shape of `sender_auth` and `payer_auth` depends only on whether the identity is named:

| `sender` | `sender_auth` | Resolved sender |
|---|---|---|
| empty | `r \|\| s \|\| v` (65 bytes) | ecrecover of the sender signature hash |
| 20-byte address | `K1_AUTHENTICATOR \|\| r \|\| s \|\| v` | `sender`; the recovered address must equal it |

Signatures must be canonical (low-s, `v` of 27 or 28). Without the Keystore, `K1_AUTHENTICATOR` is the only accepted selector, and a valid signature from the account's own key authorizes originating, paying, and delegating. Extensions may narrow that. EIP-8130 replaces the selector rule with its acceptance policy and the authorization rule with scope grants.

Sender and payer sign the same field list, through `payer`, under different type bytes (`0x79` and `0x7A`). The payer hash substitutes the **resolved** sender, which binds every payer signature, including an open one, to one specific sender.

### Payer modes

| `payer` | `payer_auth` | Mode | Resolved payer |
|---|---|---|---|
| empty | empty | Self-pay | `sender` |
| `0x00` | `r \|\| s \|\| v` | Open | ecrecover of the payer hash |
| `sender` | `K1_AUTHENTICATOR \|\| sig` | Explicit self-pay | `sender` |
| other address | `K1_AUTHENTICATOR \|\| sig` | Sponsored | `payer` |

In **open** mode the sender does not choose a payer: any key willing to pay signs the payer hash. Because the fee fields sit in the sender's signature, a third party cannot replace a pending transaction by attaching its own payer; the first valid `payer_auth` to reach a node wins. The explicit self-pay form is redundant on its own and exists so that EIP-8130's dedicated gas keys widen an existing shape rather than add a new one.

## Nonces

| `nonce_key` | Meaning |
|---|---|
| `0` | The ordinary account nonce, shared with every other transaction type |
| `1` to `NONCE_KEY_MAX - 1` | Parallel lanes held by the Nonce Manager precompile |
| `NONCE_KEY_MAX` | Nonce-free: no counter read or written |

Sharing lane `0` with legacy transactions means an EIP-8430 transaction and a type-2 transaction from the same account at the same nonce are replacement candidates for each other. Nonce-free transactions must have `nonce_sequence == 0` and a `valid_before` no more than `NONCE_FREE_EXPIRY_WINDOW` ahead; replay protection uses a fixed-capacity `replay_id` ring buffer in consensus state. `replay_id` excludes fees, `gas_limit`, and both auth blobs, so fee bumps and re-signatures do not change a transaction's identity, and the transaction hash must never be used for nonce-free deduplication. Replacement in every mode requires raising both fee fields.

## Account Changes and Delegation

| Type | Entry | Defined by |
|---|---|---|
| `0x00` | Reserved | |
| `0x01` | Delegation | EIP-8430 |
| `0x02` | Create | EIP-8130 integration |
| `0x03` | Config change | EIP-8130 integration |

A delegation entry, `rlp([0x01, target])`, sets EIP-7702-style code delegation for the sender, authorized by `sender_auth` in the same nonce stream as the calls that use it, with no separate `authorization_list` signature. That stream must be the account nonce: since a November 13 commit, a delegation entry requires `nonce_key == 0`, so a delegated account always has a non-zero nonce, as under EIP-7702. It requires native secp256k1 authentication by the account's own key, never replaces non-delegation bytecode, and clears the indicator when `target` is zero. Chains adopting EIP-8430 must support the delegation indicator even if standalone EIP-7702 transactions are disabled. **No account is ever delegated automatically**, a change from the pre-split EIP-8130 text, which auto-delegated code-less senders to a default wallet.

## Calls, Value, and Phases

Calls run directly from the sender (`msg.sender == tx.origin == sender`), each as a separate top-level frame, now with native value: `call.value` moves from the sender to `call.to` and reverts with its phase. An October 26 commit dropped the EIP-7708 transfer log the draft had emitted for value transfers. `calls` is a list of phases; calls within a phase are atomic, phases run in order from one gas pool, and the first revert stops all later phases while earlier ones persist. A typical sponsored pattern is `[[sponsor_payment], [user_action_a, user_action_b]]`.

Receipts add a `committed_phases` count, so the receipts root records which phases took effect even when they emit no logs. `status == 1` exactly when every phase committed; `status == 0` does not mean nothing happened.

`metadata` is opaque, signed, and charged like any other byte, giving attribution data the home a `tx.input` suffix used to have. The Transaction Context precompile exposes `getTransactionPayer()` for every transaction type (returning `tx.origin` outside EIP-8430), so a sponsor's phase-0 contract can confirm it is actually paying; a call costs `WARM_ACCESS` plus 3 gas per returned word. The merged text says EIP-8130 adds `getTransactionSender()` and `getTransactionSenderActorId()`, while EIP-8130's own text adds `getTransactionSender()`, `getTransactionCalls()`, and `getTransactionGasLimit()`. The two documents disagree as of November 23.

## Gas and Fees

A November 1 commit aligned the schedule with the primitives of EIP-2780 (without depending on it), so intrinsic gas is a function of the signed transaction and its resolved sender alone:

```
intrinsic_gas = AA_BASE_COST + sender_auth_cost + first_call_cost + sender_access_cost
              + value_transfer_cost + tx_payload_cost + nonce_key_cost + account_changes_cost
              + payer_auth_cost
effective_gas_limit = gas_limit + payer_auth_cost
```

| Component | Cost |
|---|---|
| `AA_BASE_COST` | 12,000 (was 15,000 before the merge): one account access, one nonce write, one balance write, plus inclusion, dispatch, settlement, and receipt |
| `sender_auth_cost` | `K1_AUTH_COST` (5,100): ecrecover plus one cold read of the signer's authorization |
| `first_call_cost` | `COLD_ACCOUNT_ACCESS` for the first call's target, mirroring EIP-2780's treatment of `tx.to`; 0 if there are no calls or it targets the sender |
| `sender_access_cost` | `COLD_ACCOUNT_ACCESS` when a different account pays (including open mode), since the base access then goes to the payer |
| `value_transfer_cost` | `TX_VALUE_COST` (6,000) per value-bearing call to another address |
| `tx_payload_cost` | 16/4 gas per non-zero/zero byte over the RLP of `account_changes`, `calls`, and `metadata` only; secp256k1 signatures are not metered |
| `nonce_key_cost` | 0 for key `0`; 22,100 when a lane's `nonce_sequence` is 0, else 5,000; `NONCE_FREE_COST` (13,000) for nonce-free |
| `account_changes_cost` | `DELEGATION_COST` (4,600) for a delegation entry |
| `payer_auth_cost` | `K1_AUTH_COST` for a payer other than self, outside `gas_limit` |

Three design choices stand out:

- **Payer authentication sits outside `gas_limit`**, so a payer's choice of `payer_auth` cannot starve the sender's calls, and `payer_auth_cost` above `MAX_AUTHENTICATION_GAS` makes a transaction invalid. Extensions that accept other authenticators must meter their authentication bytes: `sender_auth` bytes join `tx_payload_cost`, and `payer_auth` bytes add 10 gas per token.
- **An EIP-7623 calldata floor** applies to the sender's gas: `gas_used = max(sender_intrinsic_gas + execution_gas_used, sender_floor) + payer_auth_cost`, where the floor excludes nonce and account-change charges as EIP-2780 does. It closes the roughly 40% data-availability discount karlb measured on the forum (post #33) and EIP-8130 PR #12320 first fixed.
- **`K1_AUTH_COST` includes a cold authorization read** that native secp256k1 validation never performs. The merged rationale, retitled "Charging the Authorization Read," prices every authentication the same way "so an extension that stores authorizations need not reprice secp256k1 transactions."

Fees follow EIP-1559 over `effective_gas_limit`. On a base layer the schedule is a set of protocol constants (L1 profile); an L2 may reprice it but must keep the formula and the floor (L2 profile).

## Validation and Mempool

Mempool acceptance runs seven steps: structural checks (including `nonce_key == 0` for any delegation entry), sender authentication, delegation checks, payer authentication with the `MAX_AUTHENTICATION_GAS` cap, validity window and fee and balance checks including the floor, nonce or `replay_id` checks, then per-payer pending limits and replacement rules. A node may check that the sender can cover call values but should not require it, since an earlier phase can fund the sender.

Block execution verifies the nonce first, so a stale transaction fails on one read before any account change applies (a November 1 change). It then precharges the payer, applies `account_changes`, updates the nonce or records the `replay_id`, runs calls, and settles. Account changes run before the nonce update so an EIP-8130 create entry sees the sender's pre-transaction nonce. Payer authentication gas is never refundable. In RPC, `payer` uses its wire form (`0x00` for open mode), and `eth_getTransactionCount` rejects `NONCE_KEY_MAX`.

With EIP-8130 integrated, the same flow also resolves Keystore actors, applies create and config-change entries before authentication, checks scope, and enforces the policy gate and value rules. See [EIP-8130 Spec](/current-spec#consumers-and-native-integration).

## Activity

- **PR [#12385](https://github.com/ethereum/EIPs/pull/12385)**, opened September 28 and merged November 23, 2026, 20 commits. chunter-cb first self-assigned 8429; abcoathup assigned 8430 and asked for a dedicated forum thread. October 6 commits moved the Transaction Context precompile into EIP-8430. October 19 commits aligned the text with Base's implementation. Between October 23 and November 13, nine more commits specified `getNonce` for keys `0` and `NONCE_KEY_MAX`, dropped the EIP-7708 transfer log, aligned gas accounting with EIP-2780, verified the nonce before applying account changes, fixed the open-payer JSON form, charged sponsored transactions for the sender's account access, and required `nonce_key 0` for delegation. Editor jochem-brouwer approved on November 23, triggering the merge.
- **Forum thread**, opened September 30 by chunter ("Neither EIP requires the other"), six posts through October 2. chugarchugarr noted that a config-change entry's signature leaks into `replay_id`, so a re-signed identical change gets a new identity; AnkushinDaniil proposed the batch digest as the replay projection and noted EIP-8430's nonce manager overlaps EIP-8250's keyed nonces. chunter was open to per-entry replay rules and a shared nonce manager.
- **Base client**: `base/base` PRs moved activation to Everest (#5250, Sep 25), restricted it to delegation and k1-only authentication (#5232, Sep 27), and gated the Keystore separately (#5366, Sep 29). In November chunter-cb's #6388 (Nov 2) implemented the EIP-2780-aligned gas schedule, #6542 (Nov 10) the `nonce_key 0` rule for delegation, and #6552 (Nov 10) moved all hashing domains under the `0x79` prefix (`0x7900` sender, `0x7901` payer, `0x7902` replay id) because `0x7A` "could be a future EIP-2718 transaction type." The merged EIP still uses `0x7A` and `0x7901`, so Base's client and the spec diverge on signing domains as of November 23. On November 17, #6635 deleted the Keystore code and #6642 renamed the implementation "Base transactions." Everest remains unscheduled on every Base network, and Base's new [Base Transactions specification](https://docs.base.org/specifications/base-transactions) page still shows the pre-merge 15,000 base cost and calls EIP-8430 "an open proposal."
- **Drift in dependent drafts**: on November 3, jochem-brouwer's reviews of EIP-8386 and EIP-8387 flagged that both still attribute the Transaction Context precompile and account-change numbering to EIP-8130 rather than EIP-8430.
- **ERC-8168** requires EIP-8430 for its payer service.
